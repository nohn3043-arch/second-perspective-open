## 0. 读者、用途与前提

**读者**：拟集成 AAE 的对话助手 / 情感陪伴产品团队、QA 与架构评审方、第三方评测机构。

**用途**：让评估方**自行设计**测试并出具**自己的**报告，使验收不必依赖供应商自述。**随附测试套件仅作可运行的示例与对照起点：作者自测不构成第三方证据（§5）。**

**前提**：

- 核验对象为 [`../spec/SPECIFICATION-zh.md`](../spec/SPECIFICATION-zh.md) 的**接口契约**，而非任何特定实现；
- 引擎内核（`SPL-anthropic-engine.py`）属授权交付物，**不在**本公开仓库；
- 本指南描述技术核验路径，其可执行性与许可范围依 [`../LICENSE`](../LICENSE)。

## 1. 四个验证区

| 区 | 能否自证 | 工具 / 依据 | 边界 |
|---|---|---|---|
| **A 契约一致**（键集、类型、区间、入口签名） | 可自证 | 对照 [`schema/`](../spec/schema/) 校验快照与向量 | 结论仅覆盖"形状与契约一致" |
| **B 内核行为**（确定性、动力学、审计字段） | 需授权 | 引擎侧 S+R 套件 | 结论覆盖"行为与契约一致" |
| **C LLM 层**（台词生成适配器） | 不可自证 | 独立红队 / 基准 | 输出天然不可复现 |
| **D 合规端点**（未成年服务层） | 部分 | 合规说明 + 法律审查 | 生产部署另需 DPIA / 安全评估 / 算法备案 |

> **口径一句话**：A / B 区证明的是"**行为没有漂移、契约被满足**"，不证明"心理学结论正确"。前者是检测器，后者需要外部裁决。

## 2. A 区：契约一致性验证（免引擎）

任何主体无需授权即可执行：

1. 构造符合 [`schema/vector.schema.json`](../spec/schema/vector.schema.json) 的输入向量；
2. 注入虚拟时钟；
3. 施加事件序列；
4. 取出 `snapshot()`，用 [`schema/snapshot.schema.json`](../spec/schema/snapshot.schema.json) 校验：
   - 顶层键集与规范 §4.1 完全一致（不多不少）；
   - `fluid` 恰 8 键、`mood` 恰 3 键；
   - 各标量落在规范 §4.7 的区间内；
   - `信任 ≤ max_trust`。
5. 对审计记录逐行用 [`schema/audit-record.schema.json`](../spec/schema/audit-record.schema.json) 校验，并按规范 §6.3 重算 `delta`。

### 2.1 断言写法（五条规矩）

1. **观测行为，不复述公式。** 不要"读实现常量、按公式算一遍、再断言公式成立"——那对公式改动恒真。只观测"给定输入，状态怎么变"。
2. **至少一条"必须失败才算通过"的负向测试。** 例如：未注入时钟时，两次运行**必须**产生不同哈希；未知键不得改变状态。
3. **对关键断言做判别力自检。** "测试通过"只有在"把被测行为改坏后测试变红"时才是证据。在自己的副本上改一行验证，再还原。
4. **基线纪律。** 更新基线只应用于**新增向量**，不得用于让失败的旧向量变绿——那等同于删除测试。
5. **时钟纪律。** 一切重放断言先注入时钟；注入后须同步 `last_time`，否则首次时间推进会因负 `dt` 早退。任何对外声称的"可复现"**须**附带这一前提。

### 2.2 把业务场景变成向量

1. 参照规范 §3.1 的向量格式，追加你的一项；
2. 运行你的套件生成基线；`git diff` 应**只**显示新增向量的变化——若旧向量哈希也被改写，说明引擎已漂移，先查清原因；
3. 复核全绿并留档：向量文件副本 + 结果文件（含 python / platform 等环境元数据）。

产物即"该引擎在你业务序列上的可复现性证书"。

## 3. B 区：引擎内核验证（需授权）

引擎侧套件分两层：

| 层 | 内容 |
|---|---|
| **S 组** | 确定性与可重放性（含"必须不一致才算通过"的负向断言） |
| **R 组** | 语义契约：防御机制、审计归因、心境动力学、未成年变体对齐、文档一致性、变异守卫 |

> **变异守卫的意义**：注入缺陷变体后，对应测试**必须**变红。这是所有其他断言可信的前提。

**跨环境提示**：快照哈希对解释器 / 平台敏感。异构环境复核以标量层（容差 `1e-9`）为准，并在留档中声明验收环境。

## 4. 不可自证项（外部裁决）

| 声明 | 为什么不能自证 | 外部路径 |
|---|---|---|
| "行为是对的"（正确性） | 基线与被验收对象同源，是变更检测器 | 外部反事实实验：同一脚本化序列下比较 完整内核 / 机制裁剪 / 仅输出过滤 三态，人工裁决 |
| 未成年合规能力 | 技术端点可冒烟，法律义务不可自测 | 合规说明 + 法律审查 + DPIA / 安全评估 / 算法备案 |
| 依据 IMDA AI Verify 框架自评 95/100 | 提供方自测结论（非第三方、非 IMDA 官方认证） | 仓库内 `IMDA_AI_Verify_Causal_Audit_Report.pdf` |

## 5. 随附套件的性质（先读）

`tests/` 由作品作者编写——它的**执行**是第三方的（你亲自跑），但**断言设计**来自作者。因此它提供的是"行为与作者声明一致"的对照，**不构成独立证据**；真正的验收证据来自 §2 你自行设计的测试。

合理用法：可运行的示例、断言写法的参考、回归对照起点。

## 6. 报告与留档（采购场景）

建议结构：验收对象与环境（契约版本 / 环境元数据）→ 你设计的测试清单与判据 → 结果与原始工件路径 → 覆盖边界与未验证项。

| 项 | 来源 |
|---|---|
| 契约版本 | 规范文档头部版本号 |
| 验收环境（python / platform） | 你的结果文件自动记录 |
| 自定义向量 + 基线 | 你的向量文件副本（§2.2） |
| 审计日志样本 | 冒烟脚本开启审计后的 JSONL |

**复测触发条件**：引擎版本变更（语义化版本）、契约版本变更、部署形态变更。

---

## 7. 常见误用（评估红旗清单）

1. 用更新基线让失败的旧向量变绿；
2. 未注入时钟就宣称可复现，或宣称可复现但不附时钟前提；
3. 把快照哈希当作"正确性证明"（它只证"没变"）；
4. 把 LLM 层输出纳入确定性结论；
5. 依赖未接入内核的扩展模块输出（如 `tension_base`）；
6. 假设任意事件名有效（未知事件落全零分支）；
7. 以"输出过滤"替代机制级削减并声称等价；
8. 跨环境直接对比哈希而不声明环境、不用标量层兜底。
